== Decision

Hypatia should be able to compare its own findings with Codex, CodeRabbit and
pre-commit.ci without treating any external message as a proof, an approval, a
verified repair or a Bayesian success. This document specifies the first,
non-authorising boundary. It does not introduce another reviewer service or a
second parser for machine-readable formats.

This work follows the gap ledger in `docs/REVIEW-GAP-LEDGER-1009.adoc`,
the workflow-model work in
https://github.com/hyperpolymath/hypatia/issues/971[issue 971], and the
event-chain acceptance contract in
https://github.com/hyperpolymath/hypatia/issues/984[issue 984].
It does *not* close either open issue.

== What exists on this branch

* `lib/hypatia/review_observation.ex`: a pure `admit/2` function over
  structured source records and the explicitly supplied current head SHA.
  It validates known provider/scope combinations, the full reviewed SHA,
  source event identity and a GitHub URL scoped to the exact PR.
* `test/review_observation_test.exs`: positive and negative cases for
  reported findings, zero-findings reports, reviewer quotas, incomplete
  reports, head changes, evidence smuggling and distinct attempts.
* No GitHub polling, GitHub credential, filesystem writer, neural promotion,
  auto-fix, automated merge, reviewer-comment interpretation or receipt
  signing is added.

The input is a collector-normalised, string-keyed map, *not* arbitrary Markdown
or HTML from a review comment. The consumer must associate the comment and
its author with GitHub API data. A review summary's `has_findings=false` is
not a verification outcome; it is an assertion about that review's scope.

== Boundary inventory

[cols="1,3,3,3",options="header"]
|===
|Seam |Producer -> consumer |Contract |Failure treatment

|S-01
|GitHub review state -> credential-holding collector (future)
|Capture provider, exact PR, author/API event id, reviewed commit, review
scope, status and raw evidence URL; distinguish review and security streams
|No response, quota exhausted or failed review means unavailable, not clear

|S-02
|Collector -> `Hypatia.ReviewObservation.admit/2` (implemented)
|Structured map, current head, source ID generated by producer/API;
no executable text or dynamic atom creation
|Reject malformed subjects; mark stale head, pending, missing summary and
quota exhaustion without authorising actions

|S-03
|Admitted observation -> inspectable external-review ledger (future)
|Versioned record with exact event identity, subject and provenance;
strict I-JSON/JCS output, JSONL framing and canonical file profile
|No silent fallback from invalid JSON or missing provenance; dedupe source
events, not equal JSON payloads

|S-04
|External assertion -> independent symbolic verifier (future)
|Route the specific claimed defect to existing Hypatia rules, Plasma,
Pons, panic-attack, KYAML/kyq or standard-specific validators
|An untested claim remains asserted, even when two AI reviewers agree

|S-05
|Qualified remediation evidence -> OutcomeTracker/E0 (already separate)
|Verification and postcondition evidence consistent with issue 984
|External review findings and quiet reviews contribute zero learning
unless later linked to a separately qualified outcome

|S-06
|Recommendation -> fleet/dispatch (not connected here)
|Human-reviewed draft PR, exact current head, policy and proof gate
|Never promote review-provider confidence to auto-execution
|===

The S-01 and S-03 through S-06 rows are design requirements, *not claims
that integrations exist*. Sensor and dispatch remain at their documented
unverified-authenticity caps; nothing in this PR raises them.

== Admission states

[cols="2,2,3",options="header"]
|===
|Input |Assessment |Meaning

|`completed`, findings present, current head
|`reported_findings`
|Actionable lead, not a confirmed defect

|`completed`, no findings, current head
|`reported_no_findings`
|No findings were reported by that reviewer in that scope; not a security pass

|`completed`, summary unknown
|`finding_summary_missing`
|Completion without a finding verdict is not a clean review

|`quota_exhausted`, current head
|`review_unavailable_quota`
|Review did not complete regardless of any supplied finding flag

|`running`, current head
|`review_pending`
|No review decision yet

|Any status, reviewed SHA differs from current head
|`stale_head`
|May be historical evidence; cannot decide the new head

|`failed`, `cancelled`, `unavailable`
|`review_unavailable`
|Not evidence of review success
|===

Every admitted record has `evidence_class=external_assertion`,
`authenticity=unverified`, `qualification=unqualified`,
`learning_eligible=false`, `merge_approval=false`.
No input field may override these.

== Format and ownership constraints

Use https://github.com/metadatastician/standards/blob/main/3-practice/DATA-FORMAT-ROUTING.adoc[estate format routing],
not guessed filename extensions.

* GitHub Actions `.yml`: `Hypatia.Workflow` on the canonical KYAML reader
  with kyq differential fixtures; not another regex-based workflow parser.
* I-JSON/JCS: `hyperpolymath/ijson-jcs` via the estate's pinned kyq policy;
  preserve .jsonl framing. An Elixir map and `Jason.encode!` are *not*
  a canonical JCS byte receipt. Do not hash them as one.
* DEED: the current DEED ANBF, not predecessor A2ML syntax. No new .a2ml.
* K9/coordination: validate under their own standards-defined grammars;
  where applicable, check both contracts. They are not ordinary YAML.
* TOML/Dhall remain with kyq; wider projection belongs to kyX.
* Template sources, JSONC, tool-required filename exceptions and licence
  zones require contextual validation instead of blanket conversion.

The authoritative format tools are owned by their respective repositories.
Hypatia consumes pinned contracts and should emit independent conformance
failure evidence, not silently fork a competing grammar.

== Acceptance and next stage

The unit tests on this branch are necessary but do not themselves prove
review-provider authentication, JCS conformance or estate-wide detection
parity. Before promoting this to an operational review ingestion route:

. Record a GitHub API collector fixture for each provider, one per scope,
  including all four pilot classes and a quota-exhausted negative control.
. Validate raw JSON *before* lossy map decoding; canonicalise persisted
  snapshots through the pinned I-JSON/JCS executable (not a homegrown encoder).
. Give each source attempt its own stable producer event identity. Test replay,
  two identical but distinct attempts, source withdrawal and changed head.
. Add provider identity/authentication and source-event provenance checks.
  A GitHub comment's author name alone is insufficient.
. Compare independently verified pilot findings with Hypatia's own findings.
  Measure true and false positives, missed categories, unsupported rules and
  cost; do not calculate a coverage percentage when the denominator is unknown.
. Admit qualified outcomes into E0 only through the existing evidence and
  verification gates. Keep the gitbot-fleet dispatcher quarantine in force
  until its separate conditions are met.

== Known limitations and change control

No claim is made that this branch resolves the P1 findings. No toolchain
execution or CI run is implied by writing these tests; record actual runs
separately. This is a draft-PR-sized seam, deliberately isolated from the
ongoing E0 close-out and workflow-model migrations.
