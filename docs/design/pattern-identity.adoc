= Pattern identity: a key that does not depend on wording
:author: Jonathan D.A. Jewell <j.d.a.jewell@open.ac.uk>
:date: 2026-11-15
:toc:

Status: PROPOSED. The owner rules on it (section 8). No code changes in work order E0-20.

== 1. Summary

Owner ruling of 2026-11-14 on `docs/design/2026-11-14-merge-honesty.adoc`, decision 3: "a new key that does
not depend on wording, as its own design work order." This note is that work order.

What I measured, on 2026-11-15:

* The id of a pattern is the scanner rule plus the first 30 characters of the description. The description
  of the scanner has the shape `<count> <thing> in <path>`. So the id **contains the count and the start of
  the path**. In the estate registry, 824 of 1036 ids carry a count, and removing the count and the path
  leaves about 105 defect classes. One class, `PA005 unwrap-expect-calls`, is spread over 290 ids.
* A change of the count gives a new id. A fix that takes 103 calls to 102 would start a new pattern and leave
  the old one, with its recipe link, behind.
* **No recipe can match a registry id exactly.** 0 of the 42 recipe `pattern_ids` of the estate equal any of
  its 1036 registry ids. Every match today is a `category` or a `fuzzy` match.

The most correct key for the long term is one that the scanner emits: a stable id for the detector. The scanner
does not give it today. The key that I recommend now needs no scanner change, and is a step toward it.

== 3. 2 different things carry the word "pattern"

* A *pattern* is a class of defect across the fleet: "unwrap/expect calls". Recipes, confidence, the annealing stage
  and the trend are about classes.
* A *finding* is one instance: a repository, a file and a place in it. A fix, a rescan and a withdrawal are about
  instances.

Decision 3 asks for a key for the first. The fix check of `E0-22` needs the second. `E0-26` already compares the
file of a finding, and the rest is the same file, the same class, a different place. This note keeps the 2 apart
and says what each needs (section 7).

== 4. What the scanner gives

`src/types.rs` of `panic-attack` at `cbf2b93`, `WeakPoint`: `category` (30 values), `location`, `file` and `line`
(derived from `location`), `severity`, `description` (free text), `recommended_attack`, `suppressed`,
`test_context`. The canonical rule table (`WeakPointCategory::rule_id`, `PA001` to `PA029` and `PA001b`) is "a
public contract: never renumber an existing category". There is no snippet, no stable id for a detector and no
id for one instance.

== 5. Candidate keys for a pattern

Each key is listed with what it merges, what it splits, and 1 example of each.

[cols="1,3,3,3",options="header"]
|===
|Key |What it is |Keeps apart / joins |Label

|K0, today
|Hypatia's rule + first 30 characters of the description.
|Apart: a count of 103 and a count of 102 of the same defect (R2-like), the same defect in 2 directories. Joins: 2 files under one long path prefix (R4), 2 categories under `PA000` (R3).
|Rejected: it splits by count and path, joins by prefix, and depends on wording.

|K1
|The canonical `rule_id` of the scanner, alone (`PA005`).

|K2

|Apart: "unwrap/expect calls" and "unsafe get calls"; 2 unmapped categories with one description. Joins: 290 ids of one class into 1, whatever the count or the path. About 105 patterns for the estate. It still splits a reworded defect (R2), because it reads the words.
|Recommended now. It removes the measured harms and needs no scanner change. It does **not** meet "does not depend on wording" in the strict sense.

|K4
|`rule_id` + a stable id for the detector that the scanner emits (for example `PA005.unwrap`), with no
description in the key.
|Apart: 2 detectors of one rule. Joins: the same detector, whatever it says in its message. A reworded message does not split it.
|Most correct in the long term. **It needs a field that the scanner does not give today** (the stop condition of the work order): a change in `panic-attack`, which is a separate repository and a decision for you.
|===

No candidate that reads free text can be independent of wording. K4 is the only one that is. K3 is the step that
makes K4 cheap: its ids are the same shape (`PA005-unwrap-expect-calls`), so a K4 id can replace the second half
later with no change in the readers that only store or join the id. Not every reader only does that: the Kin
readers of section 7 compare ids for equality and read words inside them. A coarser K3 id can make 2 held actions
conflict that did not before, and an opaque K4 token can change what `categorize_action/1` finds. Those 2 readers
need their own check before any key is switched.

== 6. The history and the recipe link of an old pattern

* *Outcome rows.* Rows have a `pattern_id` only since `E0-18`, and older rows have none. There is no history of
  pattern ids in the outcome log to rewrite.
* *Ambiguous legacy ids.* Before mapping, identify every `PA000` id, every id whose contributing categories
  conflict in retained scans or rule-map history, and every id for which a single category cannot be established.
  `PA000` is a shared fallback (R3), so the stored category and first description cannot prove a category split.
  Hold these ids and all their occurrences out of the merge for owner review: preserve their entries and counts,
  assign no `superseded_by`, and exclude them from dispatch and recipe matching while held. Do not infer a split
  from the stored description. This proposal does not establish that retained scans cover all contributing
  findings; releasing a hold needs an owner-approved category split with evidence accounting for every occurrence
  per repository, or a separate ruling on unrecoverable data.
* *Readers before migration.* These are proposed requirements, not current behaviour: registry enumeration
  (`all_patterns`, active, category and trend queries) must skip entries with `superseded_by`; dispatch must also
  reject them even if passed directly. Explicit history access may return the original entries and counts, but
  must not feed them into live totals or dispatch. Held ambiguous entries must be identified as held in enumeration
  and excluded from dispatch as above. Implement and validate these reader rules before migrating any data.
* *The registry.* Only an old id established to contain one category maps to one new key (many-to-one for K3).
  Compute its key from that category's canonical rule and the normal form of the stored description. Keep the old
  entry marked `superseded_by`, and add its per-repository occurrences to the new key exactly once. Delete nothing;
  subsequent syncs and migration reruns must preserve the marker and must not count the old entry again.
* *Recipes and old-id lookup.* For recipe matching, resolve both the requested id and each recipe `pattern_ids`
  entry through `superseded_by` to the terminal class id before exact, category or fuzzy matching. This is separate
  from history lookup, which returns the original entry. A held id, missing alias target or alias cycle produces
  no match and a diagnostic; it must not fall back to category or fuzzy matching. An id absent from the registry
  remains a literal recipe id, preserving today's category/fuzzy matching for recipe names (0 of 42 currently
  equal registry ids). A valid alias whose canonical ids are equal is an `exact` match; otherwise category/fuzzy
  matching uses the resolved ids. After K3 a recipe can name a class id directly. The fuzzy match of `E0-21` reads
  the words after the rule: K3 keeps that shape. Implement and validate alias resolution before migration too.
* *Receipts.* `pattern_id` in a receipt is a string (`schema/receipt.ncl`). A K3 or K4 id fits.
* *A dry run first.* A script prints each eligible old id and new key, merge counts and per-repository occurrence
  totals, and writes nothing. It lists ambiguous ids separately, with the reason for each hold and its withheld
  per-repository counts; they have no proposed target and are excluded from merge totals. The migration runs only
  after the owner has seen this report and the reader and alias rules above have been implemented and validated.

== 8. What this means for the other work orders

* *`E0-22` (fix check by finding).* `E0-26` already makes the rescan judge a fix by its category and its file.
  What is left is 2 findings of one class in the same file. The fix side knows the file and not the line, and a line
  moves when the fix edits the file. The scanner gives no stable id for an instance. So that case cannot be decided
  from the rescan at all, whatever the pattern key is. **The fleet already has an identity-free answer**: its own
  postcondition counts the weak points of the recipe before and after (`before_hits` and `after_hits` in every
  fleet row; `E0-03` stores them). The fleet's verdict `verified` needs `before_hits` above 0 and `after_hits`
  equal to 0, counted by the recipe's predicate over the repository. So the recipe's own predicate judges the
  fix, and nothing has to guess which of 2 findings was meant. It answers a stricter question than the
  rescan: "did every target of the recipe go?", not "did this instance go?". When 2 instances exist and the fix
  removes one, `after_hits` stays above 0 and the verdict is `incomplete`, which is the safe side. **This does not
  meet the acceptance case of `E0-22`** (`docs/operations/e0-closeout/work-orders/E0-22-fix-check-by-finding.adoc`,
  "Acceptance"): there, the fixed finding is gone, another finding of the category stays, and the result must be
  `verified`. Option A of ruling 4 gives `incomplete` for that case and so trades the case for never reporting a
  false `verified`. Meeting the case needs an identity for the instance, which no pattern key supplies. The owner
  rules whether that trade is accepted.
* *`E0-19` (cap for a merged match).* With the registry as it is, no recipe can match exactly (0 of 42), so the cap
  would hold every dispatch at `review`. That is the intended direction, and it is also why a key like K3 matters
  to the cap. A new key alone does not change the 0 of 42: a recipe matches exactly only if its `pattern_ids` name a
  class id. Today they do not (for example `recipe-unwrap-to-match` names `PA005-panic-unwrap`,
  `PA005-unwrap-on-user-input` and `PA005-unwrap-without-check`, and none of them is a registry id, so section 6
  leaves them as literal recipe ids). The recipes in `verisimdb-data` have to be re-pointed at class ids, by a
  separate reviewed step, before the cap stops holding that class at `review`. This note does not do that step.
* *The measurement of option C* of the merge-honesty note needs a pattern that is a class. Today's ids are
  per-count and per-path, so a success rate for one id measures one count-and-path bucket, which can still join
  several files (R1, R4) and, through `repo_occurrences`, several repositories. It is not a rate for one file.

== 9. Ruling packet

Stop here. Answer by letter.

. *Which key?*
  A. K3 now, K4 later (recommended).
  B. K4 directly: the scanner emits a detector id first, and Hypatia waits.
  C. K1.
  D. Keep K0.
. *The migration of the registry.*
  A. Map eligible old ids to new keys and keep them marked `superseded_by`; hold ambiguous ids for owner review,
  with the enumeration, dispatch and recipe-resolution rules of section 6 in place, after a dry run that you have
  seen (recommended).
  B. Rebuild the registry from the scans and drop the old ids.
  C. No migration: new ids from now on, old ids left to age out.
. *If K4 is wanted:* may a work order change `panic-attack` to emit a detector id? It is a separate repository that
  you have approved for writes. I would not do it without this answer.
. *The same-file case of `E0-22`.*
  A. Judge it by the fleet's own before and after counts, and leave the rescan at the file (recommended).
  B. Wait for a stable id for the instance from the scanner. K4 does not do this: it identifies a detector
  class, so it cannot tell 2 findings of one class in one file apart (section 8).
  C. Leave the same-file case as it is, and say so.

== 10. Limits

* The "about 105 classes" is an estimate. It rests on my own normal form, applied to the first description that the
  registry kept for each id.
* The estate registry is a snapshot of one commit (sha `9d94837`). I did not scan any repository for this note.
* The examples of K1 and K2 are built from the classes that the registry shows. I did not run K1 or K2 on a scan.
* No prover was run. No code of Hypatia was changed.
