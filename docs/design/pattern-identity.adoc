Status: REVISED to the owner's rulings of 2026-11-18 (recorded as a comment on pull request 1175): the key is
K4 now (not K3 as a step), and the same-file case of `E0-22` fails closed. Questions that those rulings leave

== 1. Summary

Owner ruling of 2026-11-14 on `docs/design/2026-11-14-merge-honesty.adoc`, decision 3: "a new key that does
not depend on wording, as its own design work order." This note is that work order.

What I measured, on 2026-11-15:

* The id of a pattern is the scanner rule plus the first 30 characters of the description. The description
  of the scanner has the shape `<count> <thing> in <path>`. So the id **contains the count and the start of
  the path**. In the estate registry, 824 of 1036 ids carry a count, and removing the count and the path
  leaves about 105 defect classes. One class, `PA005 unwrap-expect-calls`, is spread over 290 ids.
* A change of the count gives a new id. A fix that takes 103 calls to 102 would start a new pattern and leave
  the old one, with its recipe link, behind.
* **No recipe can match a registry id exactly.** 0 of the 42 recipe `pattern_ids` of the estate equal any of
  its 1036 registry ids. Every match today is a `category` or a `fuzzy` match.

The key that does not depend on wording is one that the scanner emits: a stable id for the detector (K4). The
scanner does not give it today. The owner ruled (2026-11-18) that K4 is the key now, so this note recommends K4
from the start, states its cost (section 5.2: a change in `panic-attack`, and a class-id table for the old ids)
and no longer proposes the description-based key K3 as an interim step (section 5.1).

== 3. 2 different things carry the word "pattern"

* A *pattern* is a class of defect across the fleet: "unwrap/expect calls". Recipes, confidence, the annealing stage
  and the trend are about classes.
* A *finding* is one instance: a repository, a file and a place in it. A fix, a rescan and a withdrawal are about
  instances.

Decision 3 asks for a key for the first. The fix check of `E0-22` needs the second. `E0-26` already compares the
file of a finding, and the rest is the same file, the same class, a different place. This note keeps the 2 apart
and says what each needs (section 7).

=== 5.1 Why K4 and not K3

The requirement of decision 3 is a key that does not depend on wording. K3 cannot meet it, for 2 reasons that
come from how K3 is built (inferred from section 2 and the definition of K3; no K3 was run on a scan):

* K3 is a function of the text of the description. A reworded description (case R2) gives a different normal
  form, so the same defect is a new pattern and the old one loses its recipe link. The normal form removes the
  count and the path; it cannot remove a change of the words.
* The normal form is Hypatia's own reading of the scanner's free text. If the scanner changes the shape
  `<count> <thing> in <path>`, the removal of the count and the path can silently stop working. That would be a
  silent split, not a failure.

K3 is therefore *considered, not chosen*. It stays in the table as the measured fallback and as the source of the
"about 105 classes" estimate, which also bounds the size of the table that K4 needs (section 5.2). It is not an
interim step: the owner ruled against shipping a key that would be replaced and migrated a second time.

=== 5.2 What K4 costs that K3 did not

* *A field from the scanner.* `WeakPoint` (section 4) has no detector id. Until `panic-attack` emits one, no new
  finding can get a K4 key from a field. This is a change in a separate repository (section 9, question 2).
* *A class-id table for the old ids.* The 1036 old ids hold no detector id. To map an old id to a K4 key, a table
  must say which detector each old (rule, first description) belongs to. That table reads wording once, as a
  reviewed one-time artefact for the migration (about 105 rows if the estimate of section 10 holds; the
  count is not measured on the final table). It is not a runtime key. Ids that the table cannot place stay held
  (section 6). The K3 normal form would have been computed by code with no table to review.
* *A rule for a finding with no detector id.* While the scanner does not emit one, ingest cannot compute a K4
  key. Falling back to K3 would bring back what the owner ruled out; the open choice is in section 9, question 3.
* *The Kin readers.* Section 5.3.

=== 5.3 The Kin Gate and the Arbiter under K4

Facts on head `d0694ac4` (read on 2026-11-18):

* `lib/kin/gate.ex`, `check_conflict/2` (lines 417 to 427 are its search): a held action conflicts when it has the
  same `repo`, an equal `pattern_id` and a different `bot_id`. Under K4 the id names a detector, so 2 bots that
  target one detector in one repository conflict, whatever the count or the path. Under K0 they conflicted only on
  an equal count-and-path id, so this check becomes stricter. That is the intended direction of a class key, and it
  needs no code change: the comparison is equality of opaque strings.
* `lib/kin/arbiter.ex`, line 196: the same equality is a "direct conflict" resolved by priority
  (`resolve_by_priority/3`). Lines 285 to 296 (`scan_for_conflicts/2`) use equality of `pattern_id` or an overlap of
  `affected_files`. Both are equality, so K4 works without a change and is stricter in the same way.
* `lib/kin/arbiter.ex`, `categorize_action/1` (lines 254 to 275): it looks for the substrings `license`, `spdx`,
  `CommandInjection`, `PathTraversal`, `accessibility`, `a11y`, `doc` and `format` inside the `pattern_id`. The
  result feeds `non_conflicting?/2` (pairs at lines 50 to 58), which makes 2 actions on one repository compatible
  before the equality check at line 196. Two statements follow from reading the code. First, the ids that the
  registry builds today are lower case (`fingerprint/1`, `lib/pattern_registry.ex` line 380) and hold no category name,
  so the `CommandInjection` and `PathTraversal` branches cannot match a registry id (inferred from the code; I did
  not run it on the registry). Second, an opaque K4 token such as `PA005.unwrap` holds none of the words, so every
  K4 action would be `general` and no pair of `@non_conflicting_pairs` could apply. K4 therefore changes the behaviour of
  `categorize_action/1`: the pairs that today rely on a word in the description would stop being compatible.
* Both modules receive their id from `lib/fleet_dispatcher.ex` line 274, which uses `Map.get(pattern, "id",
  Map.get(pattern, "description", ""))`. A pattern with no `id` is keyed by its whole description. Under K4 that
  fallback would put a wording-dependent key into the one place that must not have it.

The code does not settle what the intended behaviour is, so these are open questions with options (section 9,
questions 4 and 5), not decisions of this note.

== 6. The history and the recipe link of an old pattern

* *Outcome rows.* Rows have a `pattern_id` only since `E0-18`, and older rows have none. There is no history of
  pattern ids in the outcome log to rewrite.
* *Ambiguous legacy ids.* Before mapping, identify every `PA000` id, every id whose contributing categories
  conflict in retained scans or rule-map history, and every id for which a single category cannot be established.
  `PA000` is a shared fallback (R3), so the stored category and first description cannot prove a category split.
  Hold these ids and all their occurrences out of the merge for owner review: preserve their entries and counts,
  assign no `superseded_by`, and exclude them from dispatch and recipe matching while held. Do not infer a split
  from the stored description. This proposal does not establish that retained scans cover all contributing
  findings; releasing a hold needs an owner-approved category split with evidence accounting for every occurrence
  per repository, or a separate ruling on unrecoverable data.
* *Readers before migration.* These are proposed requirements, not current behaviour: registry enumeration
  (`all_patterns`, active, category and trend queries) must skip entries with `superseded_by`; dispatch must also
  reject them even if passed directly. Explicit history access may return the original entries and counts, but
  must not feed them into live totals or dispatch. Held ambiguous entries must be identified as held in enumeration
  and excluded from dispatch as above. Implement and validate these reader rules before migrating any data.
* *The registry.* Only an old id established to contain one category maps to one new key (many-to-one for K4). Compute its key from that category's canonical rule and the detector id that the reviewed class-id table of section 5.2 gives for the stored description. Keep the old
  entry marked `superseded_by`, and add its per-repository occurrences to the new key exactly once. Delete nothing;
  subsequent syncs and migration reruns must preserve the marker and must not count the old entry again.
* *Recipes and old-id lookup.* For recipe matching, resolve both the requested id and each recipe `pattern_ids`
  entry through `superseded_by` to the terminal class id before exact, category or fuzzy matching. This is separate
  from history lookup, which returns the original entry. A held id, missing alias target or alias cycle produces
  no match and a diagnostic; it must not fall back to category or fuzzy matching. An id absent from the registry
  remains a literal recipe id, preserving today's category/fuzzy matching for recipe names (0 of 42 currently
  equal registry ids). A valid alias whose canonical ids are equal is an `exact` match; otherwise category/fuzzy
  matching uses the resolved ids. After K4 a recipe can name a class id directly. The fuzzy match of `E0-21` reads
  the words after the rule; a K4 id has a detector token there, not the words, so fuzzy matching against K4 ids needs its own check (not run). Implement and validate alias resolution before migration too.
* *Receipts.* `pattern_id` in a receipt is a string (`schema/receipt.ncl`). A K4 id fits.
* *A dry run first.* A script prints each eligible old id and new key, merge counts and per-repository occurrence
  totals, and writes nothing. It lists ambiguous ids separately, with the reason for each hold and its withheld
  per-repository counts; they have no proposed target and are excluded from merge totals. The migration runs only
  after the owner has seen this report and the reader and alias rules above have been implemented and validated.

== 8. What this means for the other work orders

* *`E0-22` (fix check by finding).* `E0-26` already makes the rescan judge a fix by its category and its file.
  What is left is 2 findings of one class in the same file. The fix side knows the file and not the line, and a line
  moves when the fix edits the file. The scanner gives no stable id for an instance. So that case cannot be decided
  from the rescan at all, whatever the pattern key is (K4 included: it names a detector, not an instance).
**Owner ruling, 2026-11-18: fail closed.** An ambiguous same-file case is recorded as `scan_skipped`, with no
credit and no blame on the fix, and the fleet-count answer `incomplete` is accepted. **The acceptance case of the
`E0-22` work order therefore changes: it must expect `incomplete`, not `verified`.** The fleet already has an identity-free answer: its own
  postcondition counts the weak points of the recipe before and after (`before_hits` and `after_hits` in every
  fleet row; `E0-03` stores them). The fleet's verdict `verified` needs `before_hits` above 0 and `after_hits`
  equal to 0, counted by the recipe's predicate over the repository. So the recipe's own predicate judges the
  fix, and nothing has to guess which of 2 findings was meant. It answers a stricter question than the
  rescan: "did every target of the recipe go?", not "did this instance go?". When 2 instances exist and the fix
  removes one, `after_hits` stays above 0 and the verdict is `incomplete`, which is the safe side. The work order as
  it stands (`docs/operations/e0-closeout/work-orders/E0-22-fix-check-by-finding.adoc`, "Acceptance") expects
  `verified` when the fixed finding is gone and another finding of the category stays. The ruling trades that case
  for never reporting a false `verified`. The work order is not part of this pull request's diff (the diff holds
  `docs/README.adoc` and this note), so this note does not edit it: a separate change to that file is needed to
  make its acceptance case expect `incomplete` and to record the `scan_skipped` outcome.
* *`E0-19` (cap for a merged match).* With the registry as it is, no recipe can match exactly (0 of 42), so the cap
  would hold every dispatch at `review`. That is the intended direction, and it is also why a class key such as K4 matters
  to the cap. A new key alone does not change the 0 of 42: a recipe matches exactly only if its `pattern_ids` name a
  class id. Today they do not (for example `recipe-unwrap-to-match` names `PA005-panic-unwrap`,
  `PA005-unwrap-on-user-input` and `PA005-unwrap-without-check`, and none of them is a registry id, so section 6
  leaves them as literal recipe ids). The recipes in `verisimdb-data` have to be re-pointed at class ids, by a
  separate reviewed step, before the cap stops holding that class at `review`. Owner ruling, 2026-11-18: that
  re-pointing stays a SEPARATE step. This note does not do it and the K4 ruling does not include it.
* *The measurement of option C* of the merge-honesty note needs a pattern that is a class. Today's ids are
  per-count and per-path, so a success rate for one id measures one count-and-path bucket, which can still join
  several files (R1, R4) and, through `repo_occurrences`, several repositories. It is not a rate for one file.

== 9. Ruling packet

Ruled on 2026-11-18, so no longer questions: the key is K4 now (section 5.1); the same-file case of `E0-22` fails
closed (section 8); re-pointing the recipes is a separate step. The questions below are what those rulings leave
open. Answer by letter. The option marked "(default arm)" is the most elegant and correct long-term one.

. *The migration of the registry.*
  A. Map eligible old ids to new keys and keep them marked `superseded_by`; hold ambiguous ids for owner review,
  with the enumeration, dispatch and recipe-resolution rules of section 6 in place, after a dry run that you have
  seen (recommended).
  B. Rebuild the registry from the scans and drop the old ids.
  C. No migration: new ids from now on, old ids left to age out.
. *Detector id from the scanner.* K4 needs it (section 5.2). May a work order change `panic-attack` to emit a
  stable detector id (and with what naming rule)? It is a separate repository. I would not do it without this
  answer. A (default arm): yes, a work order in `panic-attack`, with ids never renumbered, as for `rule_id`.
  B: no change; the class-id table of section 5.2 stays the only source, which keeps a wording dependence at
  ingest.
. *A finding with no detector id, until the scanner emits one.*
  A (default arm, fail closed): ingest holds it as unclassified, outside dispatch and recipe matching, and counts
  it in a visible total.
  B: look it up in the class-id table and hold only what the table cannot place.
  C: fall back to K3. This brings back the wording dependence that the ruling removed; listed for completeness.
. *`categorize_action/1` under K4.* The substring test cannot read an opaque token.
  A (default arm): the action carries an explicit `category` field (the pattern already has one; the dispatcher
  at `lib/fleet_dispatcher.ex` line 274 can pass it) and `categorize_action/1` reads that field.
  B: the detector id has a reserved, documented category segment and the test reads the segment.
  C: keep the substring test; most actions become `general` and the `@non_conflicting_pairs` stop applying.
. *Conflict scope under K4.* The Gate and the Arbiter would treat any 2 bots on one detector in one repository
  as in conflict, however far apart the instances are.
  A: accept it (equality, no code change; the stricter direction).
  B: also compare `affected_files` for that case (the Arbiter already does for different patterns, line 200
  onward). More precise, and it needs the Gate to receive `affected_files`, which it does not read today (not
  checked in detail).
  I recommend A for now. It is the simpler reading of a class key; it is not the default arm if the owner prefers
  precision, so I name both.
