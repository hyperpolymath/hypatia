== 1. What the receipt is, and what it is not

A receipt says: _this qualified event changed what a learner holds, and here is
the exact evidence that it rested on_. It names each row of evidence by a stable
id. It never names a count, because a count cannot give back its evidence
(echo-types `EchoFiniteResidue.agda`, lines 36 and 47: read in the second theory
recon, not re-run here).

* It is an index into the log that is kept. It cannot undo an update by itself.
* It is append-only. A later fact is a new receipt that links to the old one. No
  receipt is rewritten (<<d7>>).
* Timestamps and parent ids are metadata. They are not a substitute for trust.
* Every field that holds a reason is one of a closed set of values, never free
  text. The outcome of a run can show a secret, and a free-text reason is a
  channel for it (secret-types `OutcomeVisibility.agda`, `termination-sensitive-fails`).

== 2. What exists today (measured at `main`, 2026-11-14)

* The names `chain_version`, `parent_event_ids`, `subject_id` and
  `missing_evidence` occur nowhere in `lib/`, `schema/` or `src/`. `head_sha`
  occurs only in the merge orchestration (`lib/merge_orchestration/`) and in 3
  rule modules (`baseline_health`, `pr_automerge`, `research_extensions`).
* Row identity is provisional, and the code says so. A local row is named by a
  hash of the log file name and the line number
  (`LearningScheduler.local_source_id/2`, with no content in the hash). A fleet
  row is named by a hash of the line number and the line
  (`LearningScheduler.fleet_source_id/2`). Both comments say that a producer
  `event_id` will supersede them. After log rotation or truncation, a different
  local row can take the same `(file, line)`.
* The 3 places where a qualified learning update starts:
** `OutcomeTracker.update_confidence_file/5`: recomputes a recipe's confidence and
   annealing state from every qualified row in the log;
** `LearningScheduler.import_fleet_lines/2`: imports qualified fleet rows into the
   outcome log. It calls `OutcomeTracker.record_fleet_outcome`, which reaches
   `persist_outcome/6` and then the confidence update;
** `FleetDispatcher.ingest_fix_outcome/1`: feeds the neural coordinator and writes a
   row to the fleet log. It writes to a fixed path under `~/Documents/hyperpolymath-repos/gitbot-fleet/`
   and its row has no `recipe_id` and no `verification` (work order `E0-05` fixes
   the qualification; this document does not).
* Conventions that the design reuses or names:
** `schema/findings.ncl`: a Nickel contract with a derived level. A contract refuses
   a record whose stored level disagrees with its support and evidence.
** `src/Hypatia/ABI/Verdict.idr` and `Retraction.idr`, checked by
   `scripts/check-verdicts.sh` with `tests/accept/` and `tests/reject/`. `Retraction.idr`
   is the model of a thinning: a token survives exactly when its support survives.
** `lib/hypatia/ci_changed.ex`: execution receipts of local CI runs. It says that a
   local container run is not a receipt for a hosted runner, and that skipped jobs and
   missing receipts cannot certify execution.
** `verification/proof-ledger.jsonl`, checked by `scripts/proof-ledger.sh`: one
   canonical JSON object on each line, I-JSON serialised as JCS (RFC 8785), in a
   profile where `jq -cS` output _is_ the JCS form (ASCII strings, no numbers).
* Estate rules: JSON is I-JSON in JCS form. A new identifier follows ADR-008
  (`docs/decisions/ADR-008-uuid-v8-estate-standard.adoc` in `metadatastician/standards`):
  version 8, variant `10`, lowercase `8-4-4-4-12`, under profile T (time-ordered) or
  profile C (content-derived), and the field that holds it declares the profile.

== 3. The 13 fields of issue 984, step 10

Two rules apply to every row. First, a receipt has no JSON numbers: a count or a
hit number is a decimal string. That keeps the profile of the proof ledger, in
which `jq -cS` is canonical. Second, a field that E0 cannot fill is not omitted
and is not guessed: its name goes into `missing_evidence`.

The closed set of names in `missing_evidence`: `after_hits`, `before_hits`,
`event_id`, `exit_code`, `head_sha`, `match_kind`, `pattern_id`, `rescan`,
`scan_digest`, `subject_id`, `subject_identity`, `test_digest`, `tool_version`,
`verdict`. A name outside the set is refused by the contract of `E0-09`.

An integrity field `receipt_sha256` is added to each stored line: the SHA-256, in
lowercase hex, of the canonical form of all the other fields. It is not one of the
13. It covers every field of the receipt, so a field cannot change without the
digest changing. januskey's attestation (`attestation.rs`) covers the id, the time,
the type, the actor and the previous hash and not the payload; this design does
not repeat that gap. There is no previous-hash chain: writers can append at the
same time, and the order of events is carried by `parent_event_ids`.

== 4. The identity of an event

`event_id` is an ADR-008 version 8 identifier under *profile T*. Profile T is the
time-ordered layout (48 bits of Unix milliseconds, then random bits). The field
declares the profile in its type, as ADR-008 requires. Profile T needs no domain
registration. ADR-008 says that its timestamp is never used for authorisation or as
an audited event time, so the receipt carries no time field that is read from the
id.

It is minted once, by the producer, before the fix runs. It is never derived from
the content of the row: "Do not use a hash of the JSON contents as an attempt ID:
separate attempts can have identical content" (issue 984, step 6). Two attempts
with the same input get two ids, and the replay of one event keeps its id.

The estate tool is `uuid-v8 t` (the Rust command in `tools/uuid-v8/` of
`metadatastician/standards`, "Records and events"), or `scripts/uuid-v8.js` with Bun.
Whether the gitbot-fleet runner has either of them is not known from this
repository. That is a question for `E0-12`, not a gap in ADR-008: the format and
the profile are given. Hypatia mints the id of a local row with the same tool, by
`System.cmd` with an argument list and no shell, unless an Elixir generator exists
in the estate.

== 5. The 3 entry points, the start record and the failure rule

=== 5.1 Entry points

[cols="2,3,3",options="header"]
|===
|Entry point |What starts there |Where a receipt is written (decision <<d2>>, recommended option B)

|`OutcomeTracker.update_confidence_file/5`
|The recomputation of a recipe's confidence and annealing state from the log.
|Not here. It is derived from the log and can be run again. The receipt is written when the row becomes durable, in `persist_outcome/6`, which every local and imported row passes through.

|`LearningScheduler.import_fleet_lines/2`
|A fleet row enters the outcome log, through `record_fleet_outcome`.
|In `persist_outcome/6`, with the context that only the import has: the source line, the digest of the source row and the producer.

|`FleetDispatcher.ingest_fix_outcome/1`
|A fix outcome reaches the neural coordinator (`E0-05`).
|At the call to the coordinator, and only when the outcome is qualified.
|===

=== 5.2 The start record

The fleet writes the identity of an attempt before the fix runs, in a separate
append-only file next to the outcome file:
`shared-context/learning/fix-attempts.jsonl`. One line, canonical form:
`{"chain_version":"e0-receipt/1","event_id":"...","kind":"start","producer":"...","recipe_id":"...","repo":"..."}`.

* Hypatia's import reads `fix-outcomes.jsonl` and never reads `fix-attempts.jsonl`
  as outcomes. A start record is therefore not stored as an outcome, and it
  cannot make the later outcome row look like a replay.
* The same `event_id` appears in the start record and in the outcome row of the
  attempt. An attempt that never ends leaves the start record and no outcome row.
  A repair run may report such attempts as unfinished. It never credits them.
* `E0-11` still skips a record with `"kind":"start"` if it finds one in the outcome
  file, so that a producer that writes the wrong file does no harm.

=== 5.3 The failure rule

The order of writes for one qualified event is: (1) the event row, appended to the
log; (2) the receipt, appended to the receipt log; (3) the derived updates
(confidence, annealing, neural). The log row is the commit of the event. A receipt
is never written before its row: it would claim evidence that does not exist.

* If (1) fails, nothing else runs. The source is not acknowledged. This is the rule
  that `E0-06` pins for the import.
* If (2) fails, the event is committed and the derived updates do not run. The
  caller gets an error. For the import it is `{:error, {:receipt_failed, line, reason}}`,
  and the source signature does not advance, as for `write_failed`. The next run
  finds a qualified row with no receipt (see below) and writes it.
* If (3) fails, the event and its receipt exist. The recomputation is a function of
  the log, so the next learning cycle repeats it. The scheduler already retries a
  recipe from the durable log.
* *Repair.* At the start of a learning cycle, for each recipe that the cycle
  recomputes, every qualified row that has an `event_id` and no receipt gets one
  (a lookup by `event_id`, so it cannot write twice). A receipt whose `event_id`
  has no row in the log is not repaired: it is reported as corrupt, loudly.
* A row with no `event_id` (every row written before `E0-11` and `E0-12`) gets no
  receipt. Nothing is back-filled: the historical log is marked `unverified`
  elsewhere (see the README of this work-order folder).

== 6. Storage and canonical form

Receipts go to `receipts/YYYY-MM.jsonl` under the verisim-data root, beside
`outcomes/`. In tests the root is the throwaway test store of `config/test.exs`.

* One receipt on each line. Canonical form: keys sorted, no insignificant
  whitespace, one final LF, ASCII only, no JSON numbers. This is the profile of
  `scripts/proof-ledger.sh`, in which `jq -cS` output is JCS. An encoder that
  meets it is a sort of the keys and a refusal of any non-ASCII byte or number.
  The test of `E0-09` compares one encoded line with a committed fixture and with
  `jq -cS` of the same object.
* Append-only, with one `File.write(..., [:append])` for each line, as for the
  outcome log. No receipt is rewritten or deleted.
* The receipt log is not read as outcomes: `outcomes/` and `receipts/` are different
  directories, so no outcome reader sees a receipt.

== 7. The 8 decisions for the owner

Each decision lists its options. The option labelled "Recommended" is the one that I think is most correct in the long term, and I chose it. Every other option names the reason that I reject it.

[[d1]]
=== D1. The unit of a receipt

[cols="3,4,2",options="header"]
|===
|Option |Consequence |Label

|A. One receipt for each learning update: the credit of one qualified event to the learners
|Each receipt names one event and the exact row that it rests on. A recomputation that reads 400 rows makes 0 receipts, because it is derived.
|Recommended. Most correct in the long term.

|B. One receipt for each event chain (producer, import, update)

=== D6. The failure rule

[cols="3,4,2",options="header"]
|===

== 8. The properties that the Idris2 model of `E0-10` must prove

The model covers the Idris2 types. It does not cover the Elixir run time, and each
row of `verification/proof-ledger.jsonl` will say so.

[cols="1,4",options="header"]
|===
|Id |Property
|P1 |*No two receipts share an `event_id`.* Appending to a ledger that already holds an `event_id` is refused.
|P2 |*A receipt cannot claim more than its evidence.* A receipt with `qualification` `verified` cannot be built unless `proof_or_test_ref` and `observations` are present, and its `verdict` is a function of `qualification` and `claimed_outcome`, as `qualified_outcome_counts/1` computes it.
|P3 |*A revision keeps the history.* Every receipt of the ledger before a revision is a member of the ledger after it.
|P4 |*A fill never overwrites.* A gap-filling revision changes only fields that were in `missing_evidence`.
|P5 |*`missing_evidence` is exact.* The set is empty exactly when all 13 fields (and, after `E0-18`, the 2 added fields) are present.
|===

Not proved anywhere, and not claimed: that retraction is idempotent or independent
of order, and any statement about confidence. A withdrawal of a failure row raises
confidence.

== 9. What this document does not decide

* The Nickel contract, the emitter, the Idris2 model and the id reader of the fleet
  are the work of `E0-09` to `E0-12`.
* Whether the fleet runner has `uuid-v8` (question for `E0-12`).
* How a local row gets a stable id for a withdrawal (the open question of `E0-07`);
  decision D3 gives the answer for new rows.
* The cost of the repair scan on a large log: it is bounded by the recipes that a
  cycle recomputes, and no figure was measured.

== 10. Review notes (second reading, 2026-11-15)

The design above was written in one pass. A second reading against the code found
the gaps below. None of them is a ruling. Each one changes what `E0-09` can build,
so the owner should see them before ruling on <<decisions>>. The status stays
`PROPOSED`.

[cols="1,4,4",options="header"]
|===
|Id |Gap |What it changes

|R1
|*The design contradicts itself on audit rows.* The `verdict` field allows
`audit_only` (section 3), but D1 and D6 give a receipt only to a _qualified_
event, and `E0-03` now stores audit rows.
|Decide: do audit rows get a receipt? If yes, D1 becomes "one receipt for each
event that the gate reads", and the repair rule of section 5.3 must read audit rows too.
If no, remove `audit_only` from the closed set of `verdict`. Recommended (most
correct in the long term): yes, with `verdict` `audit_only`, because an audit row is
an auditable attempt (issue 984, step 9) and it is the row that is hardest to
find again.

|R2
|*The receipt must be written into the store that the row was written into.*
`OutcomeTracker.persist_outcome/6` captures the outcome store once
(`capture_outcome_store/0`) and binds every write to it, because the data root can
change at run time (the runtime-store tests of `E0` pin this). Section 6 says "under the
verisim-data root" and does not say which one.
|The receipt writer takes the captured store of the row, never the current
configuration. A receipt in another store than its row is a "receipt with no row" in
the repair rule.

|R3
|*A receipt failure and the callers' contract.* `persist_outcome/6` returns
`{:ok, record}`, and its callers match `{:ok, record} =` (`record_and_verify/5`, the
Mix task). Section 5.3 says that a failed receipt write returns an error after the row
is committed; those callers would crash with a `MatchError`, and the committed event
would be invisible to them.
|Decide the return shape before `E0-09`: for example `{:ok, record}` plus a logged
`:receipt_pending` and a repair on the next cycle, or a new return value that the
callers handle. The rule that the failure is loud (A5) is kept by the log line and by
the repair, not by a crash.

|R4
|*An absent minting tool.* D3 mints the id of a local row with `uuid-v8 t` through
`System.cmd`. Section 4 does not say what happens when the command is missing. The
same shape of fault was just fixed for the absent scanner (`#1148`): an absent tool
raised and the caller got no row.
|A missing tool gives no `event_id` and puts `event_id` in `missing_evidence`. It
never raises, and it never invents an id.

|R5
|*Cost of minting by a process for each row.* One `System.cmd` for each outcome row
is a process spawn on the write path.
|Prefer an Elixir implementation of profile T (ADR-008 lists Elixir among the
languages for the shared generators), or mint in a batch for an import. Not a
blocker; a cost to decide.

|R6
|*The echo row.* A local row is also appended to the fleet log
(`persist_outcome/6` with `publish_to_fleet?` true) and the import skips rows with
`"bot": "hypatia"`. The design does not say that the echo carries the same
`event_id` as the local row.
|The echo carries the `event_id` of the row it echoes, and `E0-11` must treat an
echo as the same event, never as a producer id.

|R7
|*The repair scan reads a whole recipe each cycle.* Section 5.3 bounds it by the
recipes that a cycle recomputes, and that is still every row of each such recipe.
|Keep a per-recipe high-water mark of the last receipted row, or accept the cost. No
figure was measured.

|R8
|*Withdrawal of a legacy local row.* D7 needs an id, and a local row written before
`E0-09` has none (the stop of `E0-07`).
|A withdrawal of a row with no `event_id` or `fleet_import_id` is refused loudly. It
is not guessed from `(file, line)`.
