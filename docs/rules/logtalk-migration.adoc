= Logtalk → Elixir Rule Migration Ledger
:toc: macro
:toclevels: 3

Status: *transcription complete in source; executable receipts pending CI*
Date: 2026-11-01
Applies to: Hypatia, ECHIDNA `rules/security_learning.lgt`, epistemic-types
`NEUROSYM.a2ml`, and the Logtalk examples vendored from standards

This is the canonical ledger for retiring Logtalk as an active rule and
report format in the Hypatia estate. It records what the Logtalk sources
meant, where each meaning now lives in Elixir, every deliberate
divergence, the exact replacement contracts for consumers, and the proof
status of the correspondence. Historical Logtalk text may remain where
this ledger classifies it as a record; it must not be read as an active
rule source or an available output format.

[WARNING]
====
The authoring sandbox for this change had no `elixir`, `mix`, `Agda`,
`idris2`, `lean`, or `coqc` binaries. The new/changed Elixir files were
syntax-parsed, and the repository proof-status/trusted-base scripts were
run, but BEAM compilation, ExUnit, Idris2 checking, and Agda checking
remain CI receipts to collect. Nothing below should be read as a local
runtime or Grade 3 proof receipt until those runs exist.
====

== Decision: the canonical rule system

Hypatia's active, canonical rule system is *pure Elixir*:

* Rule modules: `lib/rules/*.ex` (41 modules at this change), fronted by
  `lib/rules/rules.ex`.
* Generated inventory: `docs/rules/catalogue.adoc` and
  `docs/wiki-pages/Rule-Catalogue.md`, produced by
  `scripts/gen-rule-catalogue.sh` from the Elixir moduledocs. If the
  catalogue and the modules disagree, the modules win and the catalogue
  is regenerated.
* Scan findings: JSON under `schema/findings.ncl` (the CLI also renders
  `text`, `github`, and `sarif`; there is no `logtalk` format).
* Rulesets shared as data: `schemas/ruleset.schema.json`.
* Learned security-rule exports:
  `schemas/learned-security-rules.schema.json` (new in this change; see
  <<learned-rules-json>>).

There is no `engine/` tree, no Logtalk loader, and no tracked `.lgt` or
`.logtalk` source in this repository. This completes ADR-001
(2026-04-14, "Hypatia is pure Elixir") at the level of rule semantics:
ADR-001 removed the runtime; the two residual Logtalk rule sources
(ECHIDNA's fact module and Hypatia's own audit-training blocks) are
transcribed below.

== How fidelity is recorded

Each transcribed item carries one disposition:

[cols="1,3",options="header"]
|===
|Disposition |Meaning

|Exact
|Same inputs, same outputs, including failure/absence behaviour over
the stated domain.

|Operationalised
|The Logtalk condition named an uninterpreted predicate
(`crate_type(parser)`, `nearby_pattern/1`, `pr_reviews < 2`, …). The
Elixir check states the concrete evidence test used in its place; the
interpretation is written down here and in the module, not hidden.

|Extension
|The Elixir surface is a superset (more alert types, a total function
where Logtalk failed, an extra prevention mapping). Shared-domain
behaviour is unchanged.

|Superseded
|The Logtalk value was wrong or unsafe under current estate policy and
was replaced on purpose. The old value is quoted here so the change is
auditable.

|Dead code
|The Logtalk clause could never execute as written, or described a
runtime/dynamic-database mechanism replaced wholesale by an Elixir
subsystem. No clause-by-clause equivalent is pretended.
|===

== The learned-rules JSON contract

There were *two* incompatible `security_rule/4` shapes, which is
itself sufficient reason the positional format had to die:

* Hypatia's generator: `security_rule(Type, Category, AutoFix, Count)`
* ECHIDNA's exporter: `security_rule(Type, Category, Severity, AutoFix)`

The replacement is one named-field JSON document,
`schemas/learned-security-rules.schema.json` ($id
`https://hyperpolymath.dev/schemas/hypatia/learned-security-rules`,
format version `1.0.0`), produced by
`Mix.Tasks.Hypatia.BatchSecurityScan`:

[source,json]
----
{
  "schema": "https://hyperpolymath.dev/schemas/hypatia/learned-security-rules",
  "version": "1.0.0",
  "generated_at": "2026-11-01T00:00:00Z",
  "generator": "mix hypatia.batch_security_scan",
  "source_alert_count": 1234,
  "rules": [
    {
      "alert_type": "TokenPermissionsID",
      "category": "workflow_security",
      "severity": "high",
      "auto_fixable": true,
      "observations": 87,
      "fix": "Add granular workflow-level permissions ...",
      "prevention_workflow": "workflow-linter.yml"
    }
  ]
}
----

Field provenance:

[cols="1,2,2",options="header"]
|===
|JSON field |Retired Logtalk source |Canonical Elixir source

|`alert_type` |Field 1 of both shapes |GitHub/Scorecard alert id
|`category` |Field 2 of both shapes; `alert_category/2`
|`SecurityErrors.alert_category/1` (snake-case string; task-local
substring grouping only as fallback for ids outside the 18)
|`severity` |ECHIDNA field 3; `classify_severity/2` (absent from
Hypatia's generator) |`SecurityErrors.issue_severity/1`
|`auto_fixable` |Hypatia field 3 / ECHIDNA field 4; `is_auto_fixable/1`
|`SecurityErrors.auto_fixable?/1`
|`observations` |Hypatia field 4 (absent from ECHIDNA's export)
|Alert count in the producing scan. Evidence for belief formation
only — never a soundness claim (`src/Hypatia/ABI/Verdict.idr`).
|`fix` |`suggest_fix/2` |`SecurityErrors.fix_suggestion/1` (`null` when none)
|`prevention_workflow` |`get_prevention_workflow/2`
|`SecurityErrors.prevention_workflow/1` (`null` when none)
|===

All per-alert fields except `observations` are exactly
`Hypatia.Rules.SecurityErrors.validate_alert/1` rendered as JSON.

== ECHIDNA `security_learning.lgt` — clause-by-clause ledger

Source: `hyperpolymath/echidna:rules/security_learning.lgt` (only
`.lgt` file in that repository; added 2025-12-29; no loader or other
Logtalk consumer exists there). Target:
`Hypatia.Rules.SecurityErrors`, except where stated.

=== `alert_category/2` — 18 facts → `@alert_categories` — *Exact*

New canonical home: `SecurityErrors.alert_categories/0` /
`alert_category/1` (atoms, snake-case as in the Logtalk):

* `workflow_security`: TokenPermissionsID, PinnedDependenciesID,
  missing-workflow-permissions
* `code_security`: hard-coded-cryptographic-value,
  remote-property-injection, sql-injection
* `code_quality`: unused-local-variable, syntax-error
* `dependency_vuln`: VulnerabilitiesID, unmaintained
* `process_hygiene`: SecurityPolicyID, MaintainedID, CodeReviewID,
  BranchProtectionID, CIIBestPracticesID
* `missing_tests`: FuzzingID, SASTID, CITestsID

Outside these 18, `alert_category/1` returns `nil`, mirroring the
absence of a fact. (The batch-scan task keeps a separate kebab-case
*display* grouping with substring fallback for unseen ids such as
`unused-import`; it is not a second semantic source and is commented
as such.)

=== `classify_severity/2` → `issue_severity/1` — *Exact on the 18; one stated difference outside*

* critical: hard-coded-cryptographic-value, sql-injection,
  VulnerabilitiesID
* high: remote-property-injection, TokenPermissionsID,
  missing-workflow-permissions
* medium: PinnedDependenciesID, SecurityPolicyID, BranchProtectionID,
  CodeReviewID, syntax-error
* low (Logtalk catch-all `classify_severity(_, low)`): the remaining
  seven — unused-local-variable, unmaintained, MaintainedID,
  CIIBestPracticesID, FuzzingID, SASTID, CITestsID

Before this change, SASTID, CITestsID, and unmaintained had no
explicit Elixir entry and fell through to `issue_severity/1`'s `:info`
default — a silent transcription bug against the Logtalk catch-all.
They are now explicit `:low` entries. For ids *neither* system has
seen, Elixir keeps its long-standing `:info` unknown-default rather
than the Logtalk catch-all's `low`; that is the single deliberate
difference, unreachable for any of the 18.

=== `is_auto_fixable/1` — 6 facts → `@auto_fixable` — *Exact on the 18 (Elixir set is a superset overall)*

TokenPermissionsID, PinnedDependenciesID, missing-workflow-permissions,
SecurityPolicyID, BranchProtectionID, unused-local-variable. The
Elixir set additionally contains later alert ids outside the Logtalk
domain; on the 18 the two agree exactly.

=== `suggest_fix/2` — 13 facts → `@fix_suggestions`

* *Exact (10), byte-identical strings:* SecurityPolicyID,
  BranchProtectionID, CodeReviewID, CIIBestPracticesID, FuzzingID,
  VulnerabilitiesID, hard-coded-cryptographic-value,
  remote-property-injection, unused-local-variable, syntax-error.
* *Generalised (1):* PinnedDependenciesID — Logtalk
  "Replace @v4 with @SHA # v4 format" → Elixir
  "Replace @vN with @SHA # vN format" (same instruction, version
  parameterised).
* *Superseded (2):* TokenPermissionsID and missing-workflow-permissions
  — Logtalk prescribed `Add "permissions: read-all" at workflow level`.
  Current OSSF guidance (and Hypatia's own
  `scorecard_compliance/token_permissions` check) flags `read-all`
  itself as high severity, so the canonical text prescribes granular
  least-privilege permissions and explicitly warns against `read-all`.
  Transcribing the old string would have made Hypatia recommend what
  Hypatia flags.
* *No fix in either system (5 of the 18):* sql-injection, unmaintained,
  MaintainedID, SASTID, CITestsID → `fix_suggestion/1` returns `nil`.

=== `get_prevention_workflow/2` — 7 facts → `@prevention_workflows`

Exact for six: TokenPermissionsID, PinnedDependenciesID,
missing-workflow-permissions → `workflow-linter.yml`;
hard-coded-cryptographic-value → `secret-scanner.yml`;
VulnerabilitiesID → `cargo-audit.yml`; SecurityPolicyID →
`scorecard-enforcer.yml`.

* *Superseded (pre-existing, now ledgered):* BranchProtectionID —
  Logtalk `branch-protection-enforcer.yml` → Elixir
  `scorecard-enforcer.yml`. The Elixir value predates this change (it
  groups BranchProtection with the other Scorecard process checks) and
  every executable consumer has used it since; both workflow templates
  still exist under `.audittraining/prevention/`. Changing it back is
  a policy decision for a separate change, not a transcription fix.
* *Extension:* CodeReviewID → `scorecard-enforcer.yml` exists in
  Elixir with no Logtalk counterpart.

=== `cicd_integration::validate_alert/2` → `validate_alert/1` — *Total-function extension*

Logtalk composed severity + fix + auto-fixability into
`alert_validation(Type, Severity, Fix, AutoFix)` and *failed* for any
alert without a `suggest_fix/2` clause. `SecurityErrors.validate_alert/1`
returns those fields plus the separately-looked-up `category` and
`prevention_workflow`, and is total: absent facts are `nil`/`false`
rather than query failure. Consumers that relied on Logtalk failure
as an "unknown alert" signal should test `category: nil` and
`fix: nil` in the returned map (or the JSON `null`s).

=== Learning machinery — *Dead code / wholesale replacement*

`load_training_data/1`, `read_training_examples/1`,
`process_training_term/1`, `learn_rules/0`, the `training_data/3` /
`learned_rule/4` / `fix_pattern/3` dynamic database, and
`sync_from_cicd/0` (hard-coded `~/repos/cicd-hyper-a` path, Prolog
`read/1` over a Guile Scheme module) never formed a runnable pipeline
and have no clause-level equivalents. Their *purpose* is served by:

* `Hypatia.Rules.Learning` — outcome tracking, confidence, promotion
  (the live learning subsystem);
* `Mix.Tasks.Hypatia.BatchSecurityScan` — fleet alert collection and
  the learned-rules JSON above;
* `.audittraining/ERROR-CATALOG.scm` — retained as training-data
  record (Scheme, not Logtalk).

One latent ambiguity is worth recording because the JSON contract
dissolves it: `process_training_term/1` stored the catalog's second
field as `Type`, while `learn_rules/0` read the same position as
`Category`. Named JSON fields make that class of error impossible.

=== Where `.audittraining/ERROR-CATALOG.scm` disagrees with the Logtalk

The Logtalk header says its facts derive from `ERROR-CATALOG.scm`, but
the two disagree, and this transcription follows the *Logtalk* (the
values every executable consumer used), recording the Scheme variants
as open policy questions rather than smuggling them in:

* Categories: the catalog splits fuzzing/SAST/CI-tests into
  `missing-fuzzing` / `missing-sast` / `missing-tests`; Logtalk and
  Elixir use one `missing_tests` group.
* Severities: catalog has VulnerabilitiesID high (Logtalk critical),
  unmaintained medium (Logtalk low), FuzzingID/SASTID/CITestsID medium
  (Logtalk low).
* Auto-fixability: catalog marks CodeReviewID, FuzzingID, SASTID,
  CITestsID `#t`; Logtalk/Elixir say false.
* The catalog's extra entries (workflow-linter self-detection,
  rust-toolchain input, duplicate workflows, …) were never in the
  Logtalk; most already live in Elixir's extended severity/fix tables.

Adopting the catalog's finer split or medium grading would change
live severities fleet-wide and needs its own decision.

== Audit-training prevention rules AP001–AP015

Source: the `Prevention Rules (Logtalk)` blocks (2025-12-29) in seven
`.audittraining/security-errors/*.adoc` files — the last rule-bearing
Logtalk text inside Hypatia itself. Those blocks are retained in
place, now headed as historical, and are *not* executable sources.
Canonical target: `Hypatia.Rules.AuditPrevention`, whose `rules/0`
preserves every record verbatim as data (id, functor, name, effect,
description, conditions, action, origin, canonical equivalent).

Common operationalisations:

* The records had effects and actions but no severities. Finding
  severity derives from the action (`block_merge_with_escalation` →
  `:critical`; other `block_*` → `:high`; `warn_*`/`alert_*` →
  `:medium`; `warn_and_log` → `:low`). Alert-id severities remain
  `SecurityErrors`' business.
* Checks are pure functions over caller-supplied evidence (file lists,
  file contents, tag/review/score facts). `check_all/1` runs every
  implemented check whose evidence is present and is silent otherwise;
  it never duplicates a check whose canonical home is another module.

== epistemic-types `NEUROSYM.a2ml` → DEED

Artifact: `docs/rules/migration/epistemic-types_chora.deed`, to land
at the epistemic-types repository root under that exact filename
(DEED v1.2.1 dispatches the `repo-deed` head by the
`<stem>_chora.deed` filename). If that repository has acquired a repo
deed in the meantime, the single `(neurosym …)` clause merges into it
instead — a repo has one deed, not two.

Grammar authority: standards `1-formats/deed/spec/abnf/deed.abnf`
(v1.2.1); mapping authority: standards
`1-formats/deed/mappings/agentic-neurosym-playbook-to-repo-deed.adoc`
family 4. The transcription:

* `[metadata]` → `(neurosym :project :version :status :last-updated
  :author …)`, strings preserved.
* `[hypatia-config]` → `(hypatia :scan-enabled #f :scan-depth
  standard :report-format "json" :scan-paths ("src/EpistemicTypes")
  :file-globs ("*.agda"))`. Per the mapping: `scan-enabled` is a DEED
  boolean (`#f`, never the word), `scan-depth` a symbol, paths/globs
  lists of strings, DOIs would be strings (none here).
* `[neural-config] enabled=false` and `[ci] enabled=false` map
  directly to `(neural-config :enabled #f)` / `(ci :enabled #f)`.
* The one intentional semantic change in the entire file:
  `report-format` `"logtalk"` → `"json"`.

*Proposed mapping extension (needs a standards row):* family 4
currently fails closed on a populated `[symbolic-rules]` table.
epistemic-types has ten real rules, so the artifact transcribes them
as `(symbolic-rules (notes :checker-of-record … :safe-flags …) (rule

under the ABNF (clauses are generic), semantically a row standards
should ratify; see the standards coordination issue. The same applies
to the extra `[metadata]` fields carried as `:status` /

escape-for-escape so their parsed values are identical to the A2ML
(arbitrary-precision string escapes in DEED are only `\"`, `\\`, `\n`,
`\t`). The A2ML's prose comments survive as DEED comments/notes where
they carry meaning.

`--safe --without-K` flags are transcribed as-is — bringing that

cannot yet express losslessly (the mapping's fail-closed gap). It

== Guard: keeping Logtalk out

`scripts/check-no-active-logtalk.sh` (wired into CI) enforces, over
tracked files:

* no `*.lgt` / `*.logtalk` files outside the allowlist;
* no active configuration requesting Logtalk — loader paths,
`format: logtalk`, `report-format` set to `logtalk` in A2ML/DEED
form, or generated `.lgt` outputs — outside the allowlist.

Exemptions live in `.logtalk-allowlist` as *exact paths only*
(following the `.hypatia-ignore` precedent: no wildcards, no directory
blankets), each with a classification and removal condition. The list
is shrink-only: adding an entry requires the same review as adding a
rule, and the script fails if an allowlisted path no longer exists
(the classic stale-exemption rot). Historical prose mentioning
Logtalk is not banned — the guard targets executable/config forms,
and this ledger, the migration packet, the proof model, and the
seven audit-training originals are its initially allowlisted records.
Estate rollout (other repos have their own trees) is proposed through
the standards coordination issue rather than pretend-enforced from
here.
