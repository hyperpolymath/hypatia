== Checked fleet responsibilities

* gitbot-fleet, `34908580b98cd354caa3bfc5a000bc7935957fce`:
  `hooks/pre-push-gate.sh` exists and runs panic-attack/Hypatia, but missing
  scanners are explicitly skipped and zero scanners permit push. It does not
  execute each changed workflow job. The gap was not absence of a hook design;
  it was optional availability plus incomplete workflow parity.
* proven-tests-and-benches, `eafd9ad85b875e76ffd75ac3803be533364a0452`:
  `scripts/git-hooks/pre-push.sample` delegates to its owned-compute gate.
  Its test doctrine and harness/payload split fit the independent-spec corpus;
  this is not evidence that it already runs the Hypatia/kyq mutation corpus.
* cicd-squabbler, `79d7dbacc8a02b4a4388b4a36fe46893b5b7ce73`:
  README and `contracts/squabble`/`contracts/proven-tests` describe read-only
  execution/startup classification and typed evidence. Failure diagnosis is
  useful after CI; it is not evidence a new job ran before push.
* .git-private-farm, `2bba0f3763903532b286d00a9eae53fd93c67fc8`:
  the README describes mirroring and inter-repository dispatch, and says merge
  observation is manual with the actuator unwired. It is not the parser
  conformance oracle. No private configuration or credentials are needed for
  this responsibility mapping.
* proven-cicd, `eeb0a327397fe3a89ed8703caec1128260cceadb`:
  the current README identifies it as the canonical successor
  of cicd-suite, with 32 composite actions in eight clades. It explicitly
  records staged migration/canary qualification and an unpromoted GitHub
  verdict adapter. Its presence is not evidence that its entire catalogue
  runs on every repository or that a new Hypatia job ran locally.

== Local use and limits

The newly exposed standing SF001 inventory contains 15 advisory candidates
in five existing rule files. The baseline retains them as visible advisory
debt, with five exact-path entries tied to #971 and expiry 2027-02-04.
The commit and pull-request body declare this specific ledger growth using
the exemption ratchet's required `Ratchet-exception` record.
It does not use a wildcard or exempt new files. The canonical baseline gate
grades every finding at info or higher regardless of the scanner's advisory
flag, so this explicit, temporary classification is necessary to preserve
SF001's declared advisory meaning. It is not a claim that each regex is a
confirmed vulnerability or that the reader migration is complete.

Run `just ci-changed BASE` (default `origin/main`) before pushing; use
`just ci-changed-plan BASE` to inspect selection. Both committed differences
and uncommitted/untracked files are included. A shallow checkout must contain
the base commit; a missing base is an error, never an empty successful diff.
For workflow-only changes, job definitions are selected by parsed semantics,
including aliases; moving comments/line numbers does not select an otherwise
unchanged job. Any non-workflow input change conservatively selects all current
workflows, since a script or fixture can affect an unchanged job. Global
environment/event changes also select all remaining jobs. The current needs
graph is validated even when deletion would otherwise select no surviving job;
missing dependencies and cycles are errors.

The scan retains directory-scoped absence findings when a changed file is
below that directory. It applies the canonical governance baseline helper
before grading, including expiry checks, acknowledgements and overrides. Set
`HYPATIA_BASELINE_HELPER` to `scripts/apply-baseline.sh` from the same standards
revision as `governance.yml` (`a797d308c0517d4e2d21cc7f1cb08d41f82b1a12` here),
or provision it under `.standards/scripts/`. A missing helper with an active
baseline is an error. CI fetches that exact helper and explicitly includes its
integration test; other test runs exclude the provisioned-helper tag.

Existing suppressions remain active; changed files are graded at medium or
higher and SF001 remains advisory. Each job gets a supported workflow event;
`mix hypatia.ci_changed --event EVENT` can select another declared event.
Execution requests act JSON/debug logs and requires non-dry-run `jobResult`
success for the selected job. Skips, failures and absent receipts cannot count
as completion. Matrix members observed as skipped or failed invalidate the
receipt. New/changed checkout configuration, reusable jobs and write-capable
jobs require hosted validation and cause the local task to refuse a receipt.
The same blockers apply across the transitive `needs` graph before act can
run any prerequisite. Composite-action findings retain their actual root
or nested action path; workflow paths are qualified by their producer.
For other jobs, act's unchanged checkout simulation is a declared local limit;
the task does not bind a writable host workspace into the container.
Changed prerequisites select downstream consumers, and changed local reusable
contracts select their callers. Removed or repositioned checkouts also require
hosted validation. Missing or unresolved permissions, conditional steps, tolerated
failures, custom containers and secret-dependent execution cannot earn a local
receipt. The runner uses empty input/environment/secret files, an explicitly empty
GitHub token, an isolated configuration home and a cleared parent environment;
project `.actrc` files require hosted validation. Docker daemon/context and client
configuration remain available to act for container transport, without mounting
the daemon socket into job containers or loading workflow secrets from them.
These restrictions deliberately
limit local parity rather than treating simulated success as hosted evidence.
Hosted CI remains authoritative for platform-specific actions, context,
unobserved matrix expansion and permissions. A plan or mocked executor test
is not a hosted execution receipt.

The recipe is not silently installed as a Git hook in this repository or the
estate. Fleet rollout, canonical workflow-reader migration (#971) and upstream
kyq corrections remain explicit adoption work. This analysis is complete
when its ledger and conversion mechanisms are reviewed; those remaining
rollouts must not be reported as already deployed.
