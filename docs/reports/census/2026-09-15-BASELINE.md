## Severity note — why "criticality descending" is rule 2, not rule 1

Hypatia alerts carry `.rule.severity` (`"warning"`/`"error"`), **not**
`.rule.security_severity_level` (null for them). Any severity census over hypatia
alerts needs the fallback chain `.rule.security_severity_level // .rule.severity //
"none"` or it reads every hypatia alert as unclassified.

Separately, the distribution reusable's blocking gate refuses only `high` or
`critical`, so `medium`/`low`/`info` findings inflate this scoreboard but break no
merge gate.

### Two measurement caveats that must survive to the "after" run

1. **`.git-private-farm` has no code scanning.**
   `GET /repos/hyperpolymath/.git-private-farm/code-scanning/alerts` → HTTP **403**,
   *"Code scanning is not enabled for this repository."* The 3 findings hypatia's
   escript reports there are **findings, not GitHub alerts**, and the estate alert
   count does not move when they are fixed.
2. **Score with the escript, never with a replica.** A `find`-based gawk replica of the
   timeout rule reported 18 flaggable jobs in the farm where the escript reports **3** —
   a 6× over-count, because **hypatia scans only the repo-root `.github/workflows/`
   directory** (`lib/hypatia/cli.ex:401`, `:684`; no recursive walk). A fix to a template
   under `dispatch-templates/**` therefore closes **zero** alerts in that repo and is
   prevention only.
