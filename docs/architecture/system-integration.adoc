=== How To Use

==== 1. Deploy to a Repository

[source,bash]
----
# Copy workflow to repo
cp hypatia/.github/workflows/hypatia-scan-template.yml \
   your-repo/.github/workflows/hypatia-scan.yml

# Commit and push
cd your-repo
git add .github/workflows/hypatia-scan.yml
git commit -m "Add Hypatia security scanning"
git push
----

==== 2. Run Manual Scan

[source,bash]
----
# Single file
./hypatia-cli.sh scan /path/to/your/repos/svalinn/src/auth/JWT.res

# Entire repo
./hypatia-cli.sh scan /path/to/your/repos/svalinn

# Generate JSON report
HYPATIA_FORMAT=json ./hypatia-cli.sh scan . > report.json
----

==== 3. Pre-commit Hook

[source,bash]
----
# Add to .git/hooks/pre-commit
#!/bin/bash
/path/to/hypatia/hypatia-cli.sh check-staged || exit 1
----

==== 4. Fleet Coordination

[source,bash]
----
cd gitbot-fleet

# Deploy all bots
./fleet-coordinator.sh deploy-bots

# Run full scan on repo
./fleet-coordinator.sh run-scan /path/to/your/repos/svalinn

# Process pending findings
./fleet-coordinator.sh process-findings

# Check status
./fleet-coordinator.sh status
----

=== The Learning Loop

==== Observation Phase

[arabic]
. Scanner detects pattern (e.g., `+getExn+` on external data)
. Pattern recorded to
`+shared-context/learning/observed-patterns.jsonl+`
. Counter increments for this pattern

==== Threshold Phase

....
At a promote_patterns call, for one fix type     | Action
-------------------------------------------------|---------------------
fewer than 5 recorded fixes                      | not promoted
success rate below 0.75                          | not promoted
false-positive records over 30% of fix count    | not promoted
5+ fixes, success >= 0.75, FP records <= 30%    | promoted
....

The false-positive share is the number of `+record_false_positive/2+`
records for the type divided by its number of recorded fixes. A type that
is already promoted stays promoted: a later call that fails a check does
not demote it.

==== Rule Promotion and New Recipes

`+lib/rules/learning.ex+` promotes a fix type only when
`+promote_patterns+` is called; nothing in `+lib/+` calls it on a
timer. Rules for uncovered categories come from `+recipe_generator.ex+`
at confidence 0.50, and the Bayesian loop in `+outcome_tracker.ex+`
updates that confidence as fixes succeed or fail.
The Elixir rule for this pattern family lives in
`+lib/rules/code_safety.ex+`. The rules engine is 100% Elixir
(`+lib/rules/*.ex+`); see `+docs/rules/security-rule-provenance.adoc+`
for the transcribed rule tables and the learned-rules JSON contract.

=== Architecture Benefits

[arabic]
. *Feedback-driven* - Fix outcomes update confidence; rule promotion
runs when `+promote_patterns+` is called
. *Incremental* - Starts with basic rules, grows organically
. *Evidence-based* - Rules generated from actual observations
. *Self-correcting* - Failed fixes reduce pattern confidence
. *Explainable* - Every rule has observation count + context
. *Collaborative* - Bots share findings via gitbot-fleet

=== The Fire Alarm Analogy (Complete)

Before: - 🔔 Fire alarm (rules) exists - 🚒 Fire department (bots)
exists - 📞 Protocol (bot_integration) exists - ❌ Nobody watching the
alarm - ❌ Nobody calling 911 - ❌ Trucks never roll out

After: - ✅ GitHub Actions watch alarm (CI/CD) - ✅ hypatia-cli detects
smoke (scanner) - ✅ fleet-coordinator dispatches trucks (bot execution)
- ✅ robot-repo-automaton puts out fire (auto-fix) - ✅ learning_engine
improves detection (fewer false alarms) - ✅ System gets smarter with
every fire (fix outcomes feed confidence)

'''''

*The pipeline is wired end to end. Rule promotion is not automatic: it
runs when `+promote_patterns+` is called.*
