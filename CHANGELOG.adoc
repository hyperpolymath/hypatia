=== Changed

==== RE001 accepts a deed egress declaration; the job token no longer counts (2026-10-27)

The estate-wide decision on `step-security/harden-runner` (standards ADR-009) is
to declare egress instead of adopting harden-runner everywhere. RE001 now:

* ignores `secrets.GITHUB_TOKEN`, the same token as `github.token`, which it
  never counted;
* accepts a job listed in the `(egress …)` clause of the repo deed
  (`<repo>_chora.deed`) with exactly the secrets the job reads, as an
  alternative to harden-runner;
* reports drift (the declaration and the workflow disagree on secrets) and stale
  declarations (the job is gone, runs elsewhere, or reads no real secret), and
  checks a declaration even when harden-runner satisfies the job, including a
  claimed `:enforcement harden-runner-*` on a job that no longer installs it,
  and a claimed `harden-runner-block` on a step whose `with:` input (YAML
  comments aside) leaves the policy at audit;
* names the job and gives the exact `(job …)` entry in its fix text;
* reads every `${{ … }}` expression whole, even one a folded scalar splits
  across lines, and counts only the top-level `secrets` context (matched
  without regard to case), in property or index form, outside string
  literals; a read by a key computed at run time (`secrets[env.X]`,
  `toJSON(secrets)`) is its own finding, since no declaration can list it;
* reads the workflow as YAML does in two more ways: a quoted key (`"env":`,
  `'runs-on':`) is the same key, and an alias (`env: *common`, `<<: *defaults`,
  `deploy: *build`) brings its anchor's lines into the job that uses it, within
  a budget of copied lines that stops a "billion laughs" file;
* keeps #966's exposure model as the severity layer: an undeclared job is
  `:high` when the credential shares a step with fetched or untrusted code,
  and otherwise `:warn`, with or without an exposure (owner ruling
  2026-10-27: ADR-009 asks every secret-bearing job to declare).

`Hypatia.Deed` is a new reader for DEED documents (`deed.abnf` v1.2.1) and the
`(egress …)` clause profile. `test/deed_test.exs` checks it against the
standards fixtures and the template's live deed. An apg-js run of the grammar
and the reader agree on 20,043 mutated deeds, semantic checks apart.

=== Fixed

==== `mix compile` was impossible: invalid guard-as-pattern in `ActionsLock` (2026-10-25)

`lib/rules/actions_lock.ex:170` read

[source,elixir]
----
version in @supported_versions ->
----

as a bare `case` clause head. `in/2` is a guard expression, not a pattern; as a
clause head it expands to a match against `:erlang.=:=/2`, and the whole module
failed to compile:

----
error: cannot invoke remote function :erlang.=:=/2 inside a match
170 │           version in @supported_versions ->
    └─ lib/rules/actions_lock.ex:170: Hypatia.Rules.ActionsLock.consume_line/3

== Compilation error in file lib/rules/actions_lock.ex ==
** (CompileError) ... expanding macro: Kernel.in/2
----

The clause was introduced by #927 (2026-10-20) while teaching the parser to
accept `gh actions-lock` v0.0.3. It (and the `true ->` fallback beside it) was
dead code: `Regex.run/2` with one capture group always returns `[_full,
version]`, so the two `[_, version]` clauses above it already covered every
outcome — and the fallback referenced `version`, which the pattern had not
bound. The dead clauses are gone; the version is now bound by the pattern and
membership is tested in the guards, which is the only form that compiles.

Two more defects were sitting behind it in the same module, equally invisible
while it did not compile, and both are fixed here as well:

* **`@hostname` was never defined** — an unreachable second copy of the
  `hostname:` parser (the first matching `cond` arm always won) called
  `Regex.match?(@hostname, hostname)`. That attribute expands to `nil`, so the
  branch would have raised `ArgumentError` had it ever run, and it produced an
  "undefined module attribute" warning plus a typing violation that made
  `mix compile --warnings-as-errors` impossible. The dead copy is deleted; the
  surviving parser is `put_dependency_hostname/3`.
* **`finalize_dependency/1` built a map with two `hostname:` keys.** The second
  (raw `nil`) won, so *every* parsed dependency recorded `hostname: nil` and the
  seven "v0.0.3 hostname field" assertions in
  `test/rules/actions_lock_test.exs` failed. An omitted `hostname:` records
  `nil`, preserving the lockfile's recorded value; the identity check treats
  `nil` as the home host `github.com`.

Why it survived five days on `main`: nothing that gates a merge compiled the
Elixir tree. `ci.yml` had no Elixir job, `tests.yml` has `pull_request: null`,
and `escript-soundness.yml` was already red for unrelated reasons. Every
consumer's "RSR oracle — dogfood this repo" job (secret-types #11 and the rest
of the estate) died on `mix deps.get && mix compile` with this exact error and
no way to see why.

Fixed, plus the two things that let it through:

* `ci.yml` gains an **`elixir-compile` job** on the exact versions the dogfood
  gate uses (Elixir `1.19.4` / OTP `28.3`): `mix deps.get`,
  `mix compile --warnings-as-errors`, the `ActionsLock` + `RsrConformance`
  regression tests, and the consumers' oracle invocation with an explicit
  `--ssot`. It is part of `ci-status`, so it gates.
* The oracle gains a **reusable workflow**,
  `.github/workflows/rsr-oracle.yml`, which consumers pin by full commit SHA
  (`uses: hyperpolymath/hypatia/.github/workflows/rsr-oracle.yml@<sha>`) and
  which checks hypatia out at `job.workflow_sha` — the commit the caller
  pinned — so `main` is no longer the de facto release. See
  `docs/consumers/rsr-oracle.adoc`. The explicit `--ssot` contract is
  unchanged: the workflow always passes `--ssot`, defaulting to
  `<standards>/0-canon/rsr/rsr-criteria-v2.a2ml`.

=== Added

==== Group-B detectors — SD021 / WF023 / stale-issue-refs (2026-05-31, #363/#364/#366)

Three #333-cohort detectors, each a pure function taking its external signal
(injected by the caller) so they unit-test without live API access:

* **SD021** `StructuralDrift.check_workflow_branch_refs/3` (#363) — workflow
  trigger branches (`on.push`/`pull_request.branches`, inline or block form)
  that aren't in the repo's live branch list; globs and the default branch
  are exempt.
* **WF023** `WorkflowAudit.check_stale_continue_on_error/2` (#364) — a
  `continue-on-error: true` job whose "until/remove when #N" comment names an
  issue in the injected closed-issue set.
* `HonestCompletion.check_stale_issue_refs/2` (#366) — source/workflow
  comments referencing a closed/merged issue via stale-marker phrasing.

Covered by `test/rules/group_b_detectors_test.exs` (sensitivity + specificity
each). The live-signal wiring (fetching the branch list / issue states in the
scan flow) is the remaining follow-up noted on each issue.

==== `WorkflowAudit` rule `WF022` unanchored-heading-regex (2026-05-30, #360)

Flags a markdown-heading-detection regex used *unanchored* inside inline
Python in a workflow `run:` block — e.g. `re.search(r'TypeScript [Ee]xemptions', line)`
with no `^#` anchor. Such a regex also matches prose mentions of the phrase,
so the parser silently walks the wrong section. This was the multi-week
silent failure of affinescript's governance gate (`standards#183` anchored
it). HIGH severity (estate-wide, invisible in logs). Heuristic: gated on
`python3` presence, a Title-Case heading shape, and absence of `^#`
anchoring; single-word matches (`Error: (.+)`) and anchored patterns are
ignored. Threaded into `audit/3`; covered in `test/workflow_audit_test.exs`
(positive + anchored / non-heading / no-python negatives). Zero findings on
hypatia's own workflows. Cohort hypatia#333, pattern 1.

==== `WorkflowAudit` rule `WF021` concurrency-missing-readonly (2026-05-30, #365)

Flags a read-only check workflow (runs on `pull_request`/`push`, with a
`permissions:` block carrying no `: write` scope) that lacks a top-level
`concurrency:` block — rapid-push PRs then queue redundant runs. The
read-only gate plus a publisher/mutator skip-list (release, npm/jsr publish,
Pages deploy, repo mirror/sync, `git push`) keep out workflows where
`cancel-in-progress` would be unsafe. Threaded into `audit/3`; covered in
`test/workflow_audit_test.exs` for sensitivity (PR check missing concurrency)
and specificity (concurrency present, publisher, write-scoped). Verified to
produce zero findings on hypatia's own workflows. Cohort hypatia#333, pattern 6.

==== `CicdRules` rule `duplicate_cron_schedule` (2026-05-30, #362)

Flags workflows whose `on.schedule` carries redundant `cron:` triggers: two
or more entries on the same day-of-week field (e.g. three Monday crons
inherited from a workflow consolidation), or a daily `* * *` entry that
strictly covers a day-specific entry at the same `HH:MM`. Root-fixed
estate-wide in `hypatia#331` (`tests.yml`, `verify-proofs.yml`); distinct
intentional triggers (different times, or different `if:` gates on the same
day) are advisory only and never auto-removed.

Surfaced through the facade as
`Hypatia.Rules.scan_duplicate_cron_schedules/1`; the pure predicate
`CicdRules.check_duplicate_cron_schedules/2` is covered by
`test/rules/cicd_rules_duplicate_cron_test.exs` for both sensitivity
(same-day-of-week + daily-subset oracles) and specificity (different-time
non-subset, single cron, commented-out lines).

==== `WorkflowAudit` rules WF014–WF017 (2026-05-30, PRs #393 + #396)

Four new forward-detection rules surfacing patterns root-fixed in
companion `hyperpolymath/standards` PRs. All four smoke-tested for
both sensitivity (positive case fires) and specificity (inverse case
silent); see the per-rule `@doc` blocks in `lib/rules/workflow_audit.ex`
for the test matrix.

* **WF014** `scorecard_publish_with_run_step` (#393) — fires when a
  job uses `ossf/scorecard-action` with `publish_results: true` AND
  contains a `run:` step in the same job. The OSSF publish endpoint
  enforces "scorecard job must only have steps with uses"; any
  co-located `run:` step fails the publish + the whole workflow run.
  Caught 49 estate repos on the 2026-05-30 audit; template fix in
  `standards#304`.
* **WF015** `nonroot_container_checkout_eacces` (#393) — fires when
  `container.image:` is on the curated non-root-user list
  (`coqorg/coq`, `leanprover/lean4`, `makarius/isabelle`, `haskell:`,
  `rocker/r-`, `jekyll/jekyll`) AND uses `actions/checkout` AND
  lacks `container.options: --user root`. Caught ephapax `coq-build.yml`
  where the checkout post-step failed with EACCES writing
  `/__w/_temp/_runner_file_commands/` as the non-root container user.
  Does NOT fire on generic `ubuntu:22.04` / `node:18` / `alpine:latest`
  (root by default).
* **WF016** `orphan_reusable_sha_pin` (#393) — data-driven rule;
  detects callers pinning to known-orphan SHAs of
  `hyperpolymath/standards/.github/workflows/<name>-reusable.yml`.
  Initial orphan list: `hypatia-scan-reusable.yml@97df7621*` +
  `rust-ci-reusable.yml@4fdf4314*`. Caught 178 estate repos; fan-out
  recipe in `audit-hypatia-pin-orphan-2026-05-27.adoc`.
* **WF017** `secret_action_without_presence_gate` (#396) — fires
  when a workflow step uses one of the curated
  `@secret_consuming_actions` (`webfactory/ssh-agent`,
  `peter-evans/repository-dispatch`,
  `peter-evans/create-pull-request`,
  `actions-ecosystem/action-create-comment`) with `${{ secrets.X }}`
  as its primary input AND lacks an `if: secrets.X != ''` gate.
  Caught Mirror radicle (26 repos) + Instant Sync (39 repos) on the
  2026-05-30 audit; source-level fix in `standards#305`.

The `audit/3` entry point in `lib/rules/workflow_audit.ex` was
extended to thread the four new check functions into its return
`findings` list and the count summary fields.

=== Changed

==== No built-in VeriSimDB / echidnabot URLs (2026-10-08)

hypatia no longer falls back to `http://localhost:8080` (verisim-api) or
`http://localhost:9001` (echidnabot) when the service URL is unset. The new
`Hypatia.ServiceUrl` reads `HYPATIA_VERISIM_URL` and `HYPATIA_ECHIDNABOT_URL`.
A variable that is unset, empty or whitespace-only means the feature is off:
callers return `{:error, :not_configured}` (or their existing empty value)
without a network call, and nothing fails at boot.

* `ProofStrategySelection`, `StrategyDrift`, `VCL.ProofResolver`,
  `ProofObligation` prover hints and `LearningScheduler` re-queues all go
  through `ServiceUrl`.
* `Neural.ProverRecommender` used to read `VERISIM_URL` (echidna's variable)
  at **compile time**. It now reads `HYPATIA_VERISIM_URL` at runtime, like
  every other caller.
* `FleetDispatcher` reads `HYPATIA_<BOT>_URL` and `HYPATIA_FLEET_URL`
  through `ServiceUrl.from_env/1`, so a blank value counts as unset
  there too. Before, a blank per-bot URL was POSTed to as `"  /graphql"` and
  the dispatch failed instead of falling back to the fleet coordinator or
  the manifest.
* With `HYPATIA_ECHIDNABOT_URL` unset, a strategy shift logs the dropped
  re-queue candidates at info and returns `:ok`. Before this change the
  same candidates were lost against the unreachable default.

Covered by `test/service_url_test.exs`.

=== Added

==== V4f: PROOF PROVEN / SANCTIFY Resolver (2026-04-05)

`Hypatia.VCL.ProofResolver` (lib/vcl/proof_resolver.ex) parses
`PROOF PROVEN(class, prover)` and `PROOF SANCTIFY(class)` expressions
inside VCL statements and resolves them against Verisim's
`/api/v1/proof_attempts/certificates` endpoint. Supports quoted and
unquoted identifiers. Returns structured resolutions:

  {:proven,     "proven",     cert_id, success_rate, total_attempts}
  {:sanctified, "sanctified", cert_id, proven_provers, combined_attempts}
  {:pending,    cert_type,    "no data for ..."}

Also provides `resolve_all/1` which scans a VCL statement for every
PROVEN/SANCTIFY clause — suitable for the VCL executor's proof-obligation
pass.

Other proof types (EXISTENCE/INTEGRITY/PROVENANCE/CITATION/ACCESS/CUSTOM/
ZKP) continue to route through the existing proven_bridge pipeline.

==== V4e: Certified-Pair Preference in Strategy Rule (2026-04-05)

`Hypatia.Rules.ProofStrategySelection.recommend_with_certs/2` enriches
strategy output with PROVEN/PENDING status from
`/api/v1/proof_attempts/certificates` and re-sorts so PROVEN pairs
surface above uncertified ones at equal success rate.

Sort order: `cert_status` (proven > pending), then `success_rate`
(descending), then `avg_duration_ms` (ascending).

Graceful degradation: if the certs endpoint is unreachable, falls
through to plain `recommend/2` behaviour.

==== Hypatia.Neural.ProverRecommender — RBF from Live proof_attempts (2026-04-05)

First Hypatia neural module that consumes *real* post-V4 training data
instead of synthetic fixtures or findings. Trains a per-class RBF network
plus a global fallback on ~1000 samples fetched from verisim-api
(unfolded from `/strategy` aggregates since a row-level GET endpoint is
not yet implemented). Recommends provers for new obligations with
predicted success rate and confidence.

Feature vector (6-dim): `[class_score, prover_score, claim_length,
confidence, log_duration, retry_flag]`.
Target mapping: success→1.0, failure→0.0, timeout→0.25, unknown→0.5.

Live verification against 7 PROVEN certificates:
  safety/cvc5       pred=0.535 conf=0.284  (matches real 1.0×42)
  correctness/cvc5  pred=0.574 conf=0.323  (matches real 1.0×75)

Known limitations: synthetic unfolding from aggregates (row-level
endpoint pending); k-means centres collapse on homogeneous data;
no time-based decay.
